### [Rust 1.100 稳定 never 类型、自定义分配器与依赖冷却机制](https://blog.rust-lang.org/2026/11/12/Rust-1.100.0/) ⭐️ 8.0/10

Rust 1.100 正式发布，稳定了 never 类型和自定义分配器，并为 Cargo 引入依赖冷却配置（RFC 3923）：设置该配置后，解析器会忽略发布时间晚于指定时长的版本，除非这些版本已存在于 Cargo.lock 中。Cargo 现在默认以 warn 级别报告未使用的依赖，cargo install 默认使用 .crate 包内已有的锁文件，使 --locked 变为空操作。社区评论还指出，bool::toggle\(\)、Box::map\(\)、str::trim\_prefix\(\) 等稳定 API 未在发布博客中提及。

hackernews · Lobsters · 11月12日 18:39 · [社区讨论](https://news.ycombinator.com/item?id=50472038)

**「背景」** Rust 1.100 中稳定化的 never 类型（\`\!\`）与 Allocator API 都是长期跟踪的特性，此前只能在 nightly 或通过不稳定特性开关使用。Cargo 的依赖冷却机制源自 RFC 3923，该提案为 Cargo 增加了可配置的依赖版本最低发布年龄选项，用户需在 \`.cargo/config.toml\` 中主动启用。

**「对开发者的影响」** 依赖冷却配置为项目提供了一种抵御上游新版本风险的机制，但已锁定在 Cargo.lock 中的版本不受影响，因此现有项目不会因启用该配置而自动回退依赖。cargo install 默认使用包内锁文件后，依赖 --locked 行为的脚本需要确认其语义变化。

**「社区讨论」** 评论普遍肯定此次发布，有人称其为“里程碑式版本”，并感谢长期特性终于落地；也有用户抱怨编译速度慢、需要频繁 cargo clean 清理大量临时文件，但未提供具体数据。另有评论指出发布说明遗漏了多个已稳定的实用 API。

### [22 年前 Postgres 类型混淆原语被串联成代码执行](https://mehmetince.net/part-3-6-how-i-ended-up-turning-a-22-year-old-postgresql-type-confusion-primitive-into-rce-cve-2026-6460/) ⭐️ 7.0/10

安全研究者 Mehmet Ince 发布文章，详细描述如何将 PostgreSQL 中一个存在约 22 年的类型混淆原语，通过“表结构变更后仍执行过期预备语句”的路径串联为代码执行，并标注为 CVE-2026-6460。文章给出的可复现原语是：先针对某张表创建预备语句，再修改该表结构，随后执行该预备语句时，语句未按预期更新，从而触发类型混淆。作者将其称为 RCE，但文章未提供无需数据库账号即可触发的证据，实际利用需要已认证的数据库访问权限。

hackernews · ozirus · 11月12日 18:22 · [社区讨论](https://news.ycombinator.com/item?id=50471761)

**「背景」** 该漏洞已获正式编号 CVE-2026-6460。PostgreSQL 官方安全公告将其描述为 ALTER ... SET DATA TYPE 等 DDL 操作后的类型混淆，允许对象创建者以运行数据库的操作系统用户身份执行任意代码；Red Hat 的条目则指出，触发前提是已认证且拥有创建或修改数据库对象权限的用户。第三方漏洞条目给出的 CVSS 评分为 8.8，并注明当时尚无公开 PoC。

**「影响与条件」** 按评论者的分析，该问题更接近权限提升：攻击者需先持有一个数据库账号，再借此获得对整个服务器的控制，因此对多租户数据库或共享同一 Postgres 实例的环境风险更集中。运维方应关注表结构变更与预备语句缓存之间的交互，在升级或修改表后重新建立连接与预备语句，并限制数据库账号的权限范围。

**「社区讨论」** 多位评论者质疑“RCE”的定性，logophobia 和 jmuguy 认为这些利用都要求已认证的远程访问，本质是从数据库账号扩展到整台服务器，属于权限提升而非远程代码执行。ahartmetz 认为文章冗长且可能混合了 AI 写作，但指出利用思路本身很巧妙；igbanam 和 sailfast 则肯定了作者公开完整发现路径与数据库内部细节的价值。

### [Apple 推出 Foundation Models 框架，开放端侧与私有云计算模型](https://developer.apple.com/foundation-models-framework/) ⭐️ 7.0/10

Apple 的 Foundation Models 框架为开发者提供端侧模型和 Private Cloud Compute（PCC）模型的访问入口。据社区评论引述的 Apple 页面，已加入 App Store 小型企业计划、且首次下载量低于 200 万次的开发者，可在不产生云 API 费用的情况下使用运行于 PCC 的 Apple Foundation Models；在 Apple Intelligence 可用的地区，符合条件的开发者可在 App Store 分发的应用中调用 PCC，并通过 TestFlight 测试相关功能。该条目本身是框架介绍页，评论中有人质疑它是否对应一次新更新，因此具体版本与发布时间尚不明确。

hackernews · kermatt · 11月12日 21:13 · [社区讨论](https://news.ycombinator.com/item?id=50474361)

**「背景」** Apple 的 Foundation Models 框架为开发者提供统一入口，通过单一的 LanguageModelSession 将提示词路由到端侧模型、Private Cloud Compute 以及 Claude 等第三方集成。Apple 在 WWDC2026 的相关场次中介绍了通过 PCC 访问模型、集成第三方与开源模型以及视觉能力，并新增了上下文管理 API、内置语义搜索和面向智能体体验的基础组件。与此同时，Apple 在 GitHub 上开源了 coreai-models 仓库，提供模型导出配方、Python 原语和 Swift 运行时包，用于将开放权重模型适配为可在 Swift 中原生运行的格式。

**「对开发者的影响」** 对符合条件的 iOS/macOS 开发者而言，PCC 访问免云 API 费用降低了在应用中集成 Apple 模型的门槛，但资格与 App Store 分发、下载量门槛及 Apple Intelligence 可用地区绑定，需要先确认自身是否满足条件。

**「社区讨论」** 有评论者认为 Apple 的 CoreAI 工作被低估，指出 apple/coreai-models 仓库正将大量开放权重模型适配为可用 Swift 原生运行的格式；也有人分享在 M1 8GB 机器上本地运行模型做命令纠错的经验。另有评论提到 Anthropic 的 Claude 已支持 App Attest 数月，并惊讶于其推广力度不足。
